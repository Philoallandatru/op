# SSD 工程问答测试集生成指南

一条合格样本应能回答三个问题：现场同事现在要作哪个决定？他此刻能看到什么？如果照着回答执行，什么会让处置更可靠，什么会把人带错？从这三个问题出发，一次生成和复核一小批题。[研究依据与设计取舍](ssd-testset-design.md) · [74 题首问册](scenarios/engineering-questions.md) · [按主题查参考答案和评分项](README.md)

## 1. 先写工况，再选条款

1. **选事件。** 有真实工单就截取原始问法、脱敏时间线和当时已采的证据，把结案根因、修复方式和后来补采的记录留给评审侧。没有工单时，选一个工程决定并明确标为模拟。例如主机收到 Format 命令成功的 CQE，运维要不要据此给归档卷开擦除证明？这需要核实操作对象、作用范围和完成状态。
2. **做覆盖清单。** 横向按任务分，如放行业务、批准变更、归因、选择下一次采样、决定是否升级。纵向按故障族分，如供电状态切换、CQ 背压、附件一致性、固件槽位识别。优先填仍空的交叉处。一个现场只有一项待决动作，却换了三个型号或三种问法，计一个来源事件。
3. **找最少的原文。** 从实际 PDF 抄下版次、文件页、节或图表、连续英文短锚。读整段、表头、脚注及续页，标明作用域、发起端和规范强度。金标将规范事实、题设观测和工程推断分别表述。混合协议题应能指出每份规范分别解决哪一步，单一协议可以回答的题也要保留。
4. **设计第一次求助。** 只写已知：哪个控制器/命名空间、哪个传输、什么时间基准、寄存器数值从哪儿来、看到或没有捕获哪个事件。采不到某个字段和采到零要写成不同的状况。症状不必都能唯一定位根因，有时最好的交付就是暂缓某动作及一次有区分力的复测。
5. **写可接受的答案空间。** 先列结论、适用前提、可验证的下一步，再列同样正确的替代做法和会实际改变处置的误判。最后写一份简短参考回答供评审对照。合理回答无需复述相同措辞。若一项结论需要平台实测、厂商资料或另一份命令集规范，补齐来源，或把结论明确标为待确认。
6. **写追问。** 预设一个测量请求，以及至少两个能导向不同处置的可能结果。先把条件藏起来，等受测方提出等效测量再发相应观测。如果要单独测“能否利用新证据”，可直接发指定分支，并将这一成绩与“会不会主动问对问题”分开。未采集的字段应如实返回“未采集”。

## 2. 按仓库的 JSONL 格式保存

每行一题，UTF-8。新文件放在 `examples/ssd-evaluation/scenarios/` 顶层；评分导出、答卷和其他 JSONL 放在其子目录。扩展套件自动发现顶层的新增题库。可参照 [SSD-DATA-06 的完整字段](scenarios/data-integrity.jsonl#L6)。

| 字段 | 怎么写 |
| --- | --- |
| `id`, `family`, `split` | 使用稳定且全库唯一的题号。同一事件和关键条件变体归同一故障族及分组。扩展套件使用 `dev`、`challenge`。已用于调参或已公开解析的挑战题以后作为回归数据。 |
| `origin`, `source_ref` | `synthetic` 为模拟，`reconstructed` 为重建，`field` 为真实工单。后两种附可内部追查的脱敏编号。首次观测是否真实与 PDF 是否真实是两件事。 |
| `question`, `observations` | 一句现场问题和至少一项已知观测。盲投时只带问题、已知观测、题号及共同可用的版次。 |
| `decision`, `decision_sufficiency` | 短句写清要决定的事。`decidable` 表示可就题中决策给出明确意见，`conditional` 表示处置依已知边界分支，`need_observation` 表示作最终选择前还缺一项可命名的观测。后两类仍可有明确的临时处置。 |
| `root_cause_sufficiency` | `established` 表示证据确定了题目所涉的直接原因，`undetermined` 表示根因待查，`not_applicable` 用于审批、操作完成条件等不求根因的任务。 |
| `reference_answer`, `criteria`, `reject` | 每项判据有 `id, text, weight, critical, evidence`；统一一题用 10 或 100 的权重总和。只有会改变关键处置的遗漏才设为 critical。reject 写成具体错误动作或断言，引用该错说法再予以否定不触发。 |
| `evidence` | 各项填写 `id, protocol, pdf_page, section, anchor`。协议值为 `pcie` 或 `nvme`，文件页从 1 开始，本套件固定 PCIe Base 5.0 v1.0 与 NVMe Base 2.1。每条协议判据关联能支持该句的证据 ID。 |
| `followup` | 可选。含 `ask_for` 和 `branches`，每个分支含 `observation`、`expected_decision`。明确哪些数据是预设的复测结果。 |

**一个分支题的写法。** SSD-DATA-06 首问给出 A 路 Persistent Loss、B 路 Inaccessible，仅观察 5 秒，而 B 的 ANATT 为 30 秒。此时可以报告“当前无可用路径”，还不能用这 5 秒确认整组持续 all paths down。若 B 在第 12 秒转为 Non-Optimized 且可访问，判断随之更新；若完整 30 秒没有任何路径可用，则按该组 all paths down 升级。这样的题能区分三种能力：读懂当前状态、选择下一条观测、修正原来的处置。[基础依据，NVMe §8.1.2.6](https://nvmexpress.org/wp-content/uploads/NVM-Express-Base-Specification-Revision-2.1-2024.08.05-Ratified.pdf#page=505)

## 3. 把这段提示交给出题者或模型

```text
领域或工单批次 = [填入]
可用规范及版次 = [填入]
已有题库/重复检查范围 = [填入]
本批数量和目标能力 = [例如 6 题，至少 2 题第一轮不能确认根因，2 题可追加观测]

先列出候选的现场决定、它会影响谁、当时能看到什么，并与已有故障族去重。
逐项读取规范原件，选择能证明关键判断的条款，记录版本、文件页、节或图及短锚。
对每条提问写观测、正确行动、可接受替代、关键前提、误导性行动，以及最能区分原因的下一条检查。
给每条测量值标单位和时间基准，检查值域与编码。明确什么是实测、模拟或未知。
按本指南 JSONL 字段输出。只把工程师当时可见的内容放进 question 和 observations。
信息足够改变行动但不够确定根因时，分别标注。缺少决定性资料时保留缺口，不编造成功结果。
做一次反向检查：去掉一个关键观测，答案是否随之变化？新增的每项动作、时限和因果是否有依据？
```

## 4. 入库前独立复核

| 检查 | 本批可对照的例子 |
| --- | --- |
| 数值能否真的从硬件读出来？ | PCIe L1.2 的门槛要用寄存器的 Value 和 Scale 精确表达。65.536 µs 可由 64 × 1,024 ns 编码。仅让数字大小关系成立还不够。 |
| 字段描述的是不是所问对象？ | 固件槽内版本、运行镜像来自哪个槽、当前正在执行的版本是三个问题。决定“当前运行什么”应查 Identify Controller.FR。 |
| 成功、缺席和零是否被过度解释？ | 广播 Format 可在本控制器无附件时成功；其他控制器所挂归档卷的擦除证明不能据此签发。未见中断还要结合是否观察到对应 CQE 及中断消息。 |
| 给出的处置会影响谁？ | 核对控制器、命名空间、共享子系统、电源域及受影响的其他业务。评审全文中新增的复位、重试、断电、清除或重放建议，并查清它的前置条件。 |
| 两位作者会给出不同但正确的路径吗？ | 对能同样区分原因的测点照常计分。发生分歧时写清是哪项观测不足或哪种操作会改变结果，再修正判据，并对同轮各组一致重评。 |
| 工单使用规范方法还是独立量测口径？ | 明确区分两种门槛并给出原始窗口。例如规范 IDLP 的 30 秒采样从子系统空闲满 10 秒后开始；独立的台架功耗阈值要写清自己的采样起点和保持条件。规范门槛也应出现在评审原文摘录里。 |

自动校验能确认结构、同名故障族的分组以及锚点所在原文页。两位作者给相同根因取了不同族名时，还需要人工对照其关键观测和正确动作。开发与挑战可以引用同一页规范；它们考查不同场景，不能据此声称协议章节留出。发布前由独立人员同时读题面、原文、候选答案和该题所有分支。真实使用表现从去标识化工单抽取；模拟题及少见高后果题单独报告。

## 5. 运行与复用

从仓库根目录运行。先按 [README](README.md) 准备两份规范 PDF。默认套件选前八道试跑题，`extended` 选扩展题，`all` 选整套工程题。

```powershell
$kit = 'examples/ssd-evaluation'
python -X utf8 "$kit/scenario_eval.py" validate --suite all
python -X utf8 "$kit/scenario_eval.py" blind --suite all --split challenge --output "$kit/.local/challenge.jsonl"
python -X utf8 "$kit/scenario_eval.py" blind --suite all --id SSD-DATA-06 --branch 2
```

首问导出不含参考答案、证据页、评分项或后续分支。指定 `--branch` 才会给出该分支的补充观测。两轮在同一真实会话投放时，仅在第二轮发送补充观测并记录首轮索要了什么。现有 Pi 批处理会启动独立会话，将完整首问和补充观测一起送入可单测判断更新。隔离盲测会话的通用文件读取权限，保留模型版本、索引版本、实际工具访问、超时和最终答复。[Pi 运行器](pi_trial.py)

评审独立读完整答复，给每条判据 0、0.5 或 1，并选择 `ready / revise / misleading / no_answer`。本项目以“原样可用数 / 全部计划提问数”为主指标，另报“误导数 / 已交卷数”以及严重误放行的具体案例。检索命中和逐条加权分用于定位原因。追问分支另按 `update` 判其更新的决定，支持等价的安全方案。下面是一条**演示标注**，不代表本批已经跑过模型。

```json
{"id":"SSD-DATA-06","branch":2,"completed":true,"criteria":{"update":1},"reject_hits":[],"reason":"完整窗口无可用路径，按本 ANA 组升级；保留其他组和介质状态的边界。","usability":"ready","other_error":""}
```

将该行保存为 `examples/ssd-evaluation/.local/review.jsonl` 后可复核计分。只评分一个分支时分母为该次作答；同一案例的首问、两个分支和多次运行仍属于同一案例。挑战题一旦用于调参就转为回归题，从未见过的故障族或较晚工单补进下一批盲测。

```powershell
python -X utf8 examples/ssd-evaluation/scenario_eval.py score --suite extended --id SSD-DATA-06 --branch 2 --reviews examples/ssd-evaluation/.local/review.jsonl
```

## 6. 用同一道题校准评审

拿 SSD-PWR-12 试评。第一次求助只有两组数据，APST 和 ASPM 同时打开时首读慢约 2 ms，同时关闭时正常。下面三份是为校准而写的候选答复。

| 候选答复 | 可用性 | 评审依据 |
| --- | --- | --- |
| “先保留联合工单。固定空闲时长和负载，补测只开 APST、只开 ASPM；把 APST 状态表、可取得的控制器状态和链路退出轨迹与首读对时。如果只有双开复现，继续查两者交互。” | 原样可用 | 当班人能直接开展有区分力的试验，也知道单开均正常时该怎么走。 |
| “现在无法区分 APST 和 ASPM，建议再抓日志。” | 需修改 | 归因边界正确，仍缺要改变的变量、具体测点和改变派单决定的条件。 |
| “补齐两组单开对照，按时间戳看是链路还是控制器慢。PCIe 规定首读不能超过 2 ms，因此已可按违规把盘退回。” | 可能误导 | 前半段可执行，后半段把实测差值当规范期限，会触发错误退盘。即使若干评分项命中，也要登记这句额外断言。 |

把评审分歧留在记录里。例如两人都同意暂缓归因，却对“再抓日志”能否交接意见不同，就让值班同事仅凭该答复说出下一次要改哪个变量、看哪个时点。再用这个可观察的标准修正评分尺度。[SSD-PWR-12 完整题及分支](scenarios/power-link.jsonl#L12)

## 7. 把一次误答变成下一批题

保留首次原答、实际读过的证据及评审指出的错误动作。给同一模型直接提供正确条款再答一次。若它这时能提出正确处置，回看 MCP 返回的内容、排序和切段；若仍然在相同条件上归错因，检查模型如何使用前提。若两位独立工程师也无法据现有观测决定，先修正题面或把接受答案写成澄清请求。

在开发组里给这一误答增加一个变体，每次只改一条会改变决定的事实。例如原题“同时开关 APST 和 ASPM”引出了武断派单，就追加“仅打开 APST 时是否仍复现”的分支。用同一批题配对比较改动前后的原样可用数、误导数及超时数。已经讲解、调参或修过的原题与变体放回同一故障族作回归，下一轮用不同来源、未参与改进的事件检查收益。保留题库版本、规范版次和变更理由，以便还原每次对比。
