# 怎样给 SSD 现场回答出题

**主指标是工程师能原样采用的回答占全部计划提问的比例。** 把工作单位定为“一位工程师在一个时点要作的一项决定”。例如，当班同事需要决定今晚能否切电、该抓哪一段总线事务，或什么条件下可以恢复业务。现有试跑中，一份回答命中四项预设判据，额外给出的错误时限却会改变处置。题库必须能发现这种错误。[八题试跑与原始回答](reports/pilot.json)

## 从现场决定选题

从一段明确的时间窗口抽取去标识化的工单、首次求助和验证记录。同一事件被重复上报时合并，保留上报数；同一故障族里分别发生的事件保留各自的事件编号。记录平台与工作阶段。让当班工程师重述第一次求助时手上有什么、要决定什么、做错会有什么后果。由另一人把复盘结论、后续抓包和修复结果移入评审材料。按独立事件的出现频率抽取的题用来估计该窗口的使用表现。对低频而严重的处置另建挑战集，单报结果。缺少工单时可先用专家重建或模拟案例，明确来源，并保留现场表现估计为空。

TOVE 从具体场景提出知识系统必须回答的能力问题，也要求高层问题能用到简单查询的答案。FreshStack 从社区真实技术问答提取答案要点，再给要点找文档依据。本项目可据此先选工作问题，再为会改变决定的判断配证据。保留寄存器位义、条款检索等小题，用于定位错误发生在查找、理解还是应用环节。[TOVE 原文，第 2 节](https://www.eil.utoronto.ca/wp-content/uploads/public/papers/logic.pdf) · [FreshStack，NeurIPS 2025](https://proceedings.neurips.cc/paper_files/paper/2025/hash/e6b5bcc872666d37c469e5c5ba723669-Abstract-Datasets_and_Benchmarks_Track.html)

## 每个案例怎样记录

| 记录 | 编写要求 |
| --- | --- |
| 出处与分组 | 事件编号、故障族、日期、工单/重建/模拟、平台及固件版次、代表集或挑战集。同一事件的复述与变体随原题一起切分。 |
| 首问（t0） | 工程师的原话、待决动作、操作权限、时限、当时能看到的日志与时间轴。只给当时已有的观测。 |
| 证据够做什么 | 分别标明能否决定下一步、能否确认根因，列出支持每项判断的观测。明确不可等待时的处置条件。 |
| 后续观测 | 为可执行的测量写出测点、预期结果和各结果对应的动作。多轮题仅在问到等效测量时给预先固定的记录，未采集项回答“未采集”。区分实测与设想。 |
| 评审依据 | 写明可接受动作及替代路径、必要前提、停止或升级条件。逐项附规范版次、节号及适用范围，分清标准要求、建议和项目策略。为错误动作标明后果与严重度。 |

CommonKADS 的诊断模板把候选原因、值得测的量、实际取得的值和验证结论分开；Sufficient Context 研究检索上下文是否足够支持回答。上表把这两种方法用于现场记录，多标一层“现在能否作出行动决定”。同题可另作两种检查：改写同事的措辞，正确决定应保持；只改一条关键观测，预期行动应按指定方向改变。变体用于检验这一项行为。[CommonKADS，第 6 章图 6.8–6.9，书页 139–140](https://guusschreiber.nl/wp-content/uploads/2025/05/ck-book.pdf#page=156) · [Sufficient Context](https://research.google/pubs/sufficient-context-a-new-lens-on-retrieval-augmented-generation-systems/) · [CheckList，ACL 2020](https://aclanthology.org/2020.acl-main.442/)

## 样题 SSD-SHUT-01：关机超时要转给固件组吗？

模拟原题中，单功能单控制器 PCIe SSD 在 D0 收到普通关机通知，最后一次成功读取的 SHST 为 01b。主机随后将 PMCSR 切到 D3hot，再读 BAR 收到 Unsupported Request（UR）。**此时可以要求改采样顺序，固件是否卡死仍待验证。** D3hot 下该 BAR 读不会带回新状态。建议让设备保持 D0，用统一时钟记录 SHN 写入、成功的 CSTS 读取及 PMCSR 写入，再完成电源状态交接。[原题](scenarios/shutdown.jsonl) · [NVMe Base 2.1 §3.6.1](https://nvmexpress.org/wp-content/uploads/NVM-Express-Base-Specification-Revision-2.1-2024.08.05-Ratified.pdf#page=133) · PCIe Base 5.0 v1.0 §5.3.1.4.1

原题只记录到 t0。下面两条**假设的复测结果**用于检验回答能否说明每种结果将怎样改变处置。

| 复测可能得到的记录 | 工程师据此能采取的行动 |
| --- | --- |
| 保持 D0 后，成功读到 ST=0、SHST=10b。 | 本轮已观察到正常关机完成，可以交接进入 D3hot。原超时可由过早切态、失去观测窗口解释。 |
| 保持 D0，在适用等待窗口结束时仍成功读到 SHST=01b。 | 保存控制器内部轨迹，对齐主机发出 SHN 的时刻，升级调查关机耗时。已有依据指向处理延迟，最终根因仍待确认。 |

只答“多抓日志”还不足以交接。能提出等效测点并解释两个结果的路径可以通过。把 UR 解读成固件再次报告“处理中”，会造成错误归责，应在全文评审中记为误导。

## 怎样给整份回答定级

先独立读完整回答，写下“照此执行的第一步是什么，结果如何判断”。决定正确、前提可核、后续动作足以区分相关解释，且全文没有会改变处置的错误，可判**原样可用**。缺测点或前提、需要同事补写，判**需修改**。错误建议会引起误判或不当操作，判**可能误导**，并摘录原句与后果。超时无最终答复记**未回答**。所需信息确实缺失时，能问对下一条观测、交代等待期间如何处置，就可判可用。

再对照必要项，逐条核查回答自己新增的事实、动作、期限和适用条件。区分无依据、与证据矛盾和无关小错。有效替代路径交给工程师核证，同一规则对两组生效。HealthBench 用专家编写的逐题判据并与专家评分校准；FActScore 把长答案中的事实拆开核实。这里额外要求评审判断错误对当前决定的实际影响。[HealthBench 原始研究](https://openai.com/index/healthbench/) · [FActScore，EMNLP 2023](https://aclanthology.org/2023.emnlp-main.741/)

## 一轮试验需要多少工作

建议先筹集 30 个独立事件，10 个用于两位工程师独立试评、裁决分歧并冻结规则，20 个按故障族留出，优先选较晚事件。同一故障族及其变体都留在同一侧；已有八道模拟题用于开发回归。两个配置逐题配对，固定模型、题面、时间与工具预算，每配置独立跑三次。封存阶段合计 120 次作答，每组 60 次。若每份人工通读预计 6 分钟，每位全评审约需 12 小时，另计出题、校准和裁决。

隐藏系统名、调用轨迹与顺序，随机展示。模型评分器先在校准集独立评，对照两人裁决，报告四类混淆表及漏标的危险动作。封存集沿用冻结规则，以人工裁决为准，保留分歧和修订理由。每组报告原样可用数、超时数各占 60 次计划提问的比例，并分别列出代表集与挑战集的分子分母。补报误导数/已回答数、高风险案的错误放行数/应拦截次数。按事件配对报告两组差值及不确定区间；重复与变体都不能扩充独立事件数。小样本只给初步估计。

若还要验证回答有没有帮到人，可让未见过题的工程师随机在有答案、无答案两种条件下处理不同但难度配平的案例。记录其**实际选择的动作、正确率和用时**，同一人只看每个事件一次。这是对实际使用效果的另一次测量。
